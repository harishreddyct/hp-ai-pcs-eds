# Visual validation

Implementation isn't done when the page renders without errors — it's done when it's actually been checked against the live reference and the major differences have been resolved or explicitly documented. This file covers that loop, what to compare, and the accessibility and conservatism rules that apply while doing it.

**This is half of validation, not all of it.** This file covers matching the reference's appearance and behavior. `eds-performance-seo.md` covers the other half — Core Web Vitals, Lighthouse, SEO fundamentals — and is a required step here too, not an optional follow-up. A page that visually matches but hasn't had Lighthouse run against it isn't done; run both before calling a page complete.

## The loop

```
IMPLEMENT → RUN → OPEN BROWSER → INSPECT → COMPARE → IDENTIFY DIFFERENCES → FIX → RECHECK
```

Concretely, for each page and each required breakpoint (see `responsive-rules.md`):

1. Run the target application locally (or however the project is normally previewed).
2. Open the reference URL in a browser at the same viewport width.
3. Open the local implementation at the same viewport width.
4. Compare them directly — side by side if possible, otherwise back-to-back.
5. Identify concrete differences (see the comparison list below).
6. Fix the implementation.
7. Recheck the same viewport, and spot-check adjacent breakpoints to make sure the fix didn't regress them.

Repeat until major visual differences are resolved. If tooling for automated visual diffing (screenshot comparison) is available in the project or environment, use it to catch small pixel-level drift; otherwise do the comparison by careful visual inspection.

**Set up that tooling inside the target project, not borrowed from elsewhere.** If browser automation (e.g. Playwright) is needed to drive this loop or take screenshots, add it as a real `devDependency` of the project being built — with a small script (serve locally, load the page, assert the decoration pipeline ran, screenshot each breakpoint) checked in alongside the rest of the code (an EDS project's `tools/` folder, excluded from the published site the same way as other dev tooling — see the scaffold checklist in `discovery-process.md`). Never assume or reach for a browser-automation install that happens to exist in some other, unrelated project on disk — that leaves this project's validation broken the moment that other project isn't there. This applies per project: if this skill is used again on a different codebase, that codebase gets its own copy of this tooling too, not a pointer back to a previous one.

**If the user explicitly doesn't want Playwright/Lighthouse (or similar) present as physical `devDependencies`/`node_modules`, but still wants the scripts runnable**: rewrite the tool's script to shell out to the tool's own CLI via `npx` (`execFile`/`spawn`, not a bare `import`) instead of importing the package directly. Confirmed directly: `npx -p <package> node your-script.mjs` does **not** make that package resolvable to a bare `import`/`require` inside `your-script.mjs` — Node's module resolution walks up from the *script's own* directory, which never includes npx's separate temp/cache install location, so this specific pattern fails with `MODULE_NOT_FOUND` even though the package downloads successfully. What does work: invoke the package's CLI directly as a subprocess (`npx --yes lighthouse <url> --output=json ...`, `npx --yes playwright screenshot --viewport-size=W,H <url> <file>`), parsing/using its file output — both Lighthouse and Playwright ship a capable CLI for exactly this, so no project-level import is needed at all. On an EDS page specifically, add `--wait-for-timeout=2000` (or similar) to the screenshot command — EDS starts the page hidden (`body{display:none}`) and only reveals it once `scripts.js` finishes decorating and adds a `.appear` class, so a screenshot taken immediately on navigation is reliably blank. This leaves `package.json`/`package-lock.json`/`node_modules` untouched by the tool while `npm run <script>` still works end-to-end.

**Don't skip straight to "looks close enough" without actually opening both.** A page can render cleanly, have no console errors, and still be visually wrong — error-free is not the same as correct.

**A block's CSS matching the reference is not the same as the block matching the reference.** When comparing a block, diff its CSS *and* its JS against the reference's — checking only the CSS file (even a byte-for-byte match) can pass while the actual generated markup is still wrong or incomplete, because CSS rules that target elements the JS never creates simply sit there unused with no error and no visual signal that anything is missing. Concretely: if the reference's CSS has a selector (e.g. `.some-header`, `.some-icon`) that doesn't correspond to anything the local JS actually generates, that's a real, silent gap — not a false positive to dismiss. Treat an apparently-unused selector in ported CSS as a prompt to go re-read the reference's JS for what's supposed to create it, not as dead weight to ignore.

**A block's own code matching the reference is not the same as the page content built on top of it matching the reference.** Verifying `{block}.css`/`{block}.js` against the reference's copies is necessary but not sufficient — the actual authored markup fed into that block on each page (the specific divs/paragraphs/lists in the page's HTML) needs its own diff against the reference's real per-instance source. A block can be a byte-for-byte faithful port while every page using it still feeds it restructured, invented, or paraphrased content that changes how it renders (e.g. splitting one authored div into two changes which CSS rules match; paraphrasing copy instead of copying it changes the actual text; guessing which of several near-identical elements holds what content changes visual order). Re-fetch and re-read the reference's real source for the specific page/section, not just the component powering it.

**Don't drop, simplify, or "clean up" authored markup found in the reference's real source just because its purpose isn't obvious.** An empty trailing `<div></div>`, a heading that looks redundant with one already on the page, a block that seems to duplicate content structurally — these usually exist for a real (if non-obvious) reason: reserved spacing before a footer, a block that always synthesizes its own header regardless of surrounding content, etc. Reproduce what's actually there; if you genuinely can't tell why something exists, that's a reason to preserve it exactly and move on, not a reason to omit it as noise.

**Verify a resize actually took effect before trusting a screenshot at that size.** Some browser-automation resize actions only resize the outer window/chrome, not the page's actual rendered viewport — a screenshot taken right after can silently still be the previous (often desktop) layout. Confirm with a quick script-based check (e.g. reading `window.innerWidth`/`window.innerHeight` in the page) before treating the screenshot as evidence of mobile/tablet behavior. If resize can't be confirmed to work in the current environment, fall back to reading the implementation's and the reference's actual CSS media queries as ground truth for responsive correctness instead of an unreliable screenshot — it's slower to reason through but won't quietly mislead you the way a stale screenshot will.

## What to compare

- Overall layout and content order
- Component dimensions (width, height, aspect ratios)
- Spacing (margins, padding, gaps between elements)
- Typography (font, size, weight, line height, letter spacing)
- Colors (backgrounds, text, borders — against actual values, not eyeballed)
- Borders and shadows
- Images (cropping, scaling, aspect ratio, placement)
- Alignment
- Responsive behavior at the breakpoint being checked
- Navigation (structure and, where testable, interaction)
- Content positioning within sections
- Whitespace/rhythm between sections
- Interaction states (hover, focus, active, open/closed) wherever they can be observed and reproduced
- Icons and small decorative graphics specifically: check whether the reference renders a real vector icon (inline SVG, icon font, `<img>`) versus what got built. A text/emoji glyph standing in for one ("▶", "→", a Unicode arrow) is a common shortcut that looks passably similar in a quick read but renders with different proportions, weight, and anti-aliasing than a real vector icon — treat any glyph substitution as a placeholder to verify against the reference's actual markup, not as done
- The actual authored content structure for each page/section against the reference's real source (element nesting, how many instances of a repeating item exist, which content lives in which instance) — not just whether the resulting component looks approximately right

## Measure, don't eyeball

By the time you reach this validation pass, you should already have extracted the reference's measurements in Phase 3.5 (see `references/measurement-extraction.md`) and built against them. This pass is a **diff against that recorded spec**, not a first-time extraction — confirm the implementation's computed values match the measurements you took before building. If this pass surfaces a value you never extracted in Phase 3.5, that's a gap in the spec: add the measurement to the measurements document, don't just patch the one symptom. The rules below apply identically whether you're extracting a value the first time (Phase 3.5) or confirming it here — either way the value comes from `getComputedStyle()`/`getBoundingClientRect()` on the live reference, never from reading a screenshot.

A screenshot tells you what a page *looks like*, not what its actual CSS values are — and several specific failure modes below were only caught once real computed styles were pulled programmatically (`getComputedStyle()` via a headless browser, or the network/DOM inspection tooling available in the environment) instead of read off a rendered image. Treat this as required for typography, color, and layout-breakpoint claims specifically, not just a nice-to-have:

### Header/nav chrome needs the same breakpoint sweep as page content

It's easy to measure a header/logo/nav bar once (often at whatever width is convenient) and treat that as settled, since it's "chrome" rather than page content and looks done once it renders without errors. Confirmed directly: a reference's header height and logo size were constant from 375px up to 1024px, then both jumped together (117px → 194px header, 96px → 128px logo) at exactly this project's own 1200px tier and stayed constant above it — a real, second breakpoint state that a single-width check of "the header" would never surface. Sweep header/nav/footer chrome across the full required breakpoint range exactly like any other component, including elements (utility bar height, logo size, nav padding) that feel like fixed constants rather than "content" worth re-checking per breakpoint.

**Chrome also has *scroll* states, not just breakpoint states — scroll the page and re-measure the header/footer, don't only measure at scroll position 0.** A sticky/fixed header commonly *shrinks or transforms on scroll* (collapses a utility bar, reduces its height, swaps a large logo for a small one), which a static top-of-page measurement can never surface because it isn't a function of viewport width at all — it's triggered by `scrollY`. Confirmed directly: a reference header was `position: fixed` and shrank from 194px to 114px once scrolled (its dark utility bar collapsing), while the implementation was `position: sticky` and stayed a constant 194px — the breakpoint sweep had matched the at-rest height perfectly and still missed the entire scroll behavior. For any sticky/fixed chrome, take a second measurement pass *after* scrolling the page (e.g. `window.scrollTo(0, 600)`), diff the scrolled height/position/inner-element sizes against the reference's scrolled state, and reproduce the transition. Note also that `position: fixed` vs `position: sticky` are not interchangeable when the chrome resizes on scroll: `sticky` keeps the element in normal flow so a height change reflows the page, whereas `fixed` takes it out of flow (and then the content needs its own top offset) — match whichever the reference uses, or pick `sticky` + an animated height transition if a small reflow is acceptable.

### "Fluid" and "full-bleed" elements can still have an upper cap — check widths beyond the top breakpoint tier, not just at it

This skill's fixed breakpoint scale (768/960/1200) defines the tiers to build for, but it isn't the full range of widths the page will actually be viewed at — a wide or ultra-wide monitor renders well past 1200px, and an element that looks correctly fluid or edge-to-edge at every defined tier can still hit an uncovered fixed cap above them. Confirmed directly on a reference site at 1440/1728/1920px (checked because the user's own screenshots were taken on a wide display, and every prior check had stopped at ~1280px): a "full-bleed" hero image actually caps at a fixed max-width and starts centering with margins beyond it, and a caption card assumed to scale fluidly with the viewport was instead completely fixed-width from 1200px up through 1920px+, growing to fill nearly the whole viewport in this project's build instead of staying put. If a project will realistically be viewed on wide desktop displays, take at least one measurement pass above the top defined tier (e.g. 1440px and 1920px) specifically for "fluid" or "full-bleed" elements — those are exactly the ones most likely to hide an unmeasured cap, precisely because they look like they shouldn't need one.

### A property confirmed on one instance of a component isn't confirmed on every instance

The same visual component can appear multiple times across a site with per-instance authored properties (an eyebrow label, a badge, an icon) that don't automatically carry over just because the underlying block/CSS is shared. Confirmed directly: a "feature card" component's `eyebrow` property was correctly added on the magazine-listing page's instance but silently missing from the home page's instance of the exact same component — the CSS and block code were identical and correct on both, but the per-page authored content wasn't. When a fix or property is confirmed correct on one page's use of a shared component, explicitly check every other page using that same component for the same property, rather than assuming a shared component's fix propagates to all its instances.

### Never inherit a spacing/sizing value from an earlier build phase without re-confirming it

A surprising, high-impact source of mismatches on a real project: a `.section`-level (or other shared-container) padding value that was invented during an early mock-content phase — before any real measurement was ever taken — silently survived every later, more careful pass because no one had a reason to suspect the *container* itself, only the content inside it. Confirmed directly: a project's `.section` rule carried 40-64px of its own vertical padding that had never once been checked against the reference, and the reference measures **zero** padding-top/bottom on every section's full ancestor chain, at every breakpoint, on every page — all real vertical rhythm between sections comes from heading/paragraph margins alone. This one unverified rule was responsible for a large, previously unexplained excess gap between literally every section on every page. **Any spacing value that was set before real measurement began (i.e. during initial scaffolding, a mock-content pass, or copied from a generic template) is a placeholder, not a fact, regardless of how long it's been in the codebase or how many other passes have gone by without flagging it** — the exhaustive audit above needs to include shared layout/container rules, not just the content elements sitting inside them.

**A shared container with zero vertical padding can let a child's margin escape it via CSS margin collapsing, showing up as a gap *before* the container instead of inside it.** If a heading is the first child of a padding-less, border-less box, its `margin-top` collapses through that box (and will keep collapsing through further nested padding-less ancestors) rather than creating space between the box's own top edge and the heading — confirmed directly by finding a container's top edge and its first heading's top edge landing on the exact same pixel, meaning the heading's margin had already escaped upward. If measurement shows a heading's own `margin-top` is real and non-zero but the visual gap isn't appearing where expected, check whether the container and heading's rendered top edges coincide (a sure sign of collapse) before concluding the margin isn't being applied. Fix with `display: flow-root` (or an equivalent new block-formatting-context trigger) on the container — it contains the margin correctly without needing artificial padding to fake the same effect, and doesn't need any other layout side effects to achieve it.

**A value confirmed at one breakpoint is not confirmed at another — measure at mobile width specifically, not just wherever's convenient, given this skill's mobile-first priority.** A component's font-size, line-height, or padding can differ meaningfully between mobile and desktop in ways that aren't obvious from the desktop view alone (confirmed: a card's description text was 14px at mobile widths but 18px at desktop — a value measured once at desktop and assumed to hold everywhere was wrong at the size that matters first). Whenever a project is built or validated mobile-first, the *first* real measurement of any given element should be taken at the narrowest required width, with wider breakpoints checked as explicit deltas from that baseline — not the other way around.

### Run an exhaustive measurement audit, not reactive spot-checks

The single biggest reason real mismatches survive multiple "looks good" passes is **spot-checking**: measuring only the one element a screenshot made you suspicious of, instead of measuring everything. Spot-checking can only find what you already suspect is wrong — it structurally cannot catch a bug in something you never thought to look at (a hero image sized by viewport-height instead of aspect-ratio, a card grid that stretches instead of staying a fixed width, a caption card capped at the wrong width by a *second* rule you didn't know existed — all three shipped, and re-shipped, on the same real build until an exhaustive pass caught them).

Before calling any page's visual validation complete, run one comprehensive pass instead: for **every** image, heading, paragraph, and button-styled element on the page, pull its rendered box (`getBoundingClientRect()`) and relevant computed styles (`font-size`, `font-weight`, `line-height`, `color`, `margin`, `padding`, `text-transform`), at **every** required breakpoint — for the reference and for the implementation — and diff the two sets programmatically rather than reading two screenshots side by side.

**Every block gets its own measured pass — a block you never suspected is exactly the one that ships wrong.** The measurement audit is worthless if it silently skips blocks. Confirmed directly: a project's `team` block (About Us portraits) shipped 128px circular photos against the reference's 164px, with a muted sentence-case role line against the reference's uppercase near-black one and a single large CTA against the reference's row of three small icon buttons — none of it caught, because the measurement pass had covered the header, hero, and cards and the registry was then written up as though the whole site had been measured. "I ran the measurement audit" is only true if it covered **every** block instance the page renders, not a representative-feeling subset. Make this checkable: give the component registry a "Measured" state per block, and don't let a block reach `complete` without a recorded measurement pass (which breakpoints, when) behind it — an unmeasured block is `not verified`, however finished its code looks.

**Never infer a grid/layout variant from the number of items in it.** A section with three cards is not evidence of a three-column component — the reference may lay those three into the *same* multi-column track every other listing uses and simply leave the trailing cell(s) empty. Confirmed directly: a "WKND Guides" section's three members were read as a bespoke 3-column `guides` variant when the reference actually renders them in its ordinary 4-column contributor grid with an empty fourth cell; the invented variant then diverged from the shared grid at other breakpoints. Before creating any variant to explain an item count, measure a card's rendered width against the base grid's track width — if they match, it's the same grid under-filled, not a new variant. A variant needs a *measured structural difference* (different track width, different card size, different gap), not just a different number of things. **`margin` (particularly `margin-top` on headings) is easy to leave off this list and easy to get wrong**: a project-wide "reset" convention (e.g. a global `h1..h6 { margin: 0 0 Xpx }` giving every heading `margin-top: 0`) can look like reasonable, tidy CSS authorship while being flatly contradicted by the reference, which may give headings real, non-zero top margin that varies by context (confirmed: a reference's teaser/card-embedded heading carried `margin-top: 0.5em` while its container's own padding-top was genuinely zero — the heading's own margin was the *entire* source of breathing room above it, and a `margin-top: 0` reset silently deleted it). Don't assume any "obviously correct" reset value is safe without measuring it against the reference specifically. A small reusable script that walks `document.querySelectorAll('img, h1, h2, h3, h4, p, a, button')` (filtering to visible, meaningful elements) and dumps this per breakpoint is enough; it doesn't need to be fancy, it needs to be *exhaustive*. Do this once, early, across the whole page — not only after a user reports a specific mismatch.

**Measure the seams between regions — especially the content→footer seam — not just the regions themselves.** An exhaustive audit that measures every block's own box can still miss the *space between* the last block and the global footer, because that gap belongs to neither block and no per-block pass ever looks at it. Confirmed directly: a build shipped the dark footer flush against the last content on every page (`footer` `margin-top: 0`) while the reference put a fixed 48px gap above the footer on every page — a site-wide seam mismatch that every component-level measurement pass sailed past because each component was individually correct. For every page, measure the vertical distance from the last content element's bottom to the footer's top (and the footer's own `margin-top`/`padding-top`) against the reference, at every breakpoint. Global chrome seams (content→footer, header→content) are their own audit target, distinct from the blocks on either side of them.

**Measure each region's horizontal content inset (left/right gutter) at every breakpoint, not just its vertical seams.** The seam audit above catches vertical gaps; it says nothing about how far a region's content sits from the left and right screen edges, and that gutter is its own recurring mismatch — especially on a full-bleed dark footer bar where under-sized side padding reads as content "hugging the edges." Confirmed directly: the footer shipped a *fixed* 16px side gutter that matched the reference at 1200px+ (where both cap at a centered max-width) but hugged the edges at 1024px and below, where the reference keeps a ~28–32px gutter — a mismatch invisible at the one wide width that got checked. For header, every content section, and the footer, measure the left inset (content-left minus region-left) and right inset (region-right minus content-right) at every required breakpoint and diff against the reference. A region whose gutter is a fixed constant while the reference's *grows* with viewport will only match at whatever width you happened to test; sample at least a narrow (≤768), a mid (~1024), and a wide (≥1280) width before trusting it.

**A hero/banner caption that overlaps the image is part of the hero block — author it there, never as a separate section below.** When the reference renders a short heading + intro paragraph on a card that overlaps the bottom edge of a hero image (pulled up over the image via negative margin), that text is the hero's own teaser caption, not a standalone content section that follows the hero. Confirmed directly: the adventures page's "Experience the world with us" intro first shipped *missing* (dropped by the content-completeness diff below), then shipped as a standalone flat-text `plain-title` section below an image-only hero — both wrong; the reference authors it *inside* the hero (image cell + caption cell in the same hero row, rendered as a ~1192px white card overlapping the hero bottom). The tell is vertical overlap in the layout skeleton: a text block whose top y sits *above* the previous image region's bottom y is one composed unit with that image, not the next section. When a hero is followed closely by a short heading+paragraph, check for the overlap and, if present, move the text into the hero's own authored row rather than leaving it a following section — the caption then also correctly skips any per-section heading treatment (e.g. the yellow underline), because it's block content, not a section heading.

**A thin rule or divider near the page bottom is usually authored content, not footer chrome — and it renders differently in EDS.** The reference may place a content-width horizontal rule between the last content and the footer on *some* pages (a listing page, an article) but not others (home, a contact page). Don't add it globally because it appears on the page you happened to screenshot, and don't assume it's part of the footer — measure which pages actually have it (its color, width, and which content width it aligns to), then reproduce it only there. In EDS specifically, a markdown thematic break (`---`) is the *section separator* and renders invisibly (it just splits sections), so a visible divider has to come from CSS — a section style applied via `section-metadata` on exactly the pages the reference has it — not from authoring an `<hr>` and expecting it to show.

**Run a content-completeness diff, not just a styling diff.** Styling audits catch elements that render wrong; they say nothing about text that's missing, renamed, or misplaced. Extract the reference's ordered text outline for the page — every heading and paragraph inside `main`, in document order — and diff it one-to-one against the implementation's. Confirmed directly on a single About Us pass: a section heading shipped as "Contributors" against the reference's "Our Contributors", one intro paragraph was attached to the wrong heading, and a second intro paragraph was dropped entirely — three separate content defects, none of which any dimension/font measurement would ever surface, all of which a five-line ordered-text diff catches at once. Do this for every page, alongside the measurement audit, before calling it complete. It catches two failure modes that recur on *listing* pages specifically: (1) a short intro/lede section (a heading + one paragraph) sitting between the hero and the item grid gets dropped entirely because attention jumps straight from "there's a banner" to "there's a card grid" — confirmed: an adventures listing shipped without its "Experience the world with us" H2 + intro paragraph, which sat between the hero and the cards on the reference; and (2) a section heading is reproduced with plausible-but-wrong wording — confirmed: the same listing's grid heading shipped as "All adventures" against the reference's "Current Adventures". The outline diff must compare heading *text* exactly, not just confirm a heading of that level exists.

When this audit surfaces a real difference, verify the fix the same way: re-measure the actual rendered value after changing the CSS, don't just confirm "I edited the rule that looked responsible." A property can be set by more than one rule at different specificity or media-query layers — fixing the one that seems relevant and stopping there missed a *second*, differently-scoped rule (a base mobile-first rule, still active at desktop widths, that a desktop-only override never touched) still capping the same element. If the rendered value doesn't match after your edit, there is another rule still winning; go find it rather than assuming the fix "should" have worked.

**Don't assume a common responsive pattern (breakpoint-driven column counts, a 50/50 flex split, cards stretching to fill their container) without measuring the actual mechanism.** A reference site can use a genuinely different, less obvious pattern — e.g. a fluid flex-wrap layout where every card stays a *fixed* pixel width at every breakpoint and only the column count changes, which looks similar to a stretching grid in a single screenshot but produces different card sizes at in-between viewport widths. Measure multiple items' bounding rects across at least three breakpoints before committing to a layout mechanism, not just the number of columns visible in one screenshot.

**Scope a spacing/typography fix to exactly what you measured — don't generalize it to every similar-looking element on the page.** The temptation once you've confirmed one heading needs `margin-top: 0.5em` is to fix the shared base rule so *every* heading gets it. Check first whether that's actually warranted: other headings elsewhere on the same page can have a measurably *different* value (a standalone section heading vs. one embedded in a teaser/card are legitimately different contexts), or may already have a different, pre-existing mismatch in the opposite direction (already too much gap) that a blanket fix would make worse, not better. Apply the fix at the narrowest selector the measurement actually supports (the specific block/component context), and treat "does this same property differ in other contexts on the page" as its own thing to check before touching a shared/global rule.

**A wrapping element between a sized container and the element you're actually styling can silently break a percentage-based size.** `height: 100%` on an `<img>` resolves against its *direct* parent's height — if that direct parent is a `<picture>` element (common in a responsive-image markup pattern) and nothing has explicitly sized `picture` itself, the percentage resolves against `picture`'s own auto/intrinsic height instead of the grandparent container you actually sized, and the image silently doesn't stretch. If a percentage-based size isn't taking effect, check what the element's *actual* parent is (not what you assume the containing block is) before concluding the CSS property itself doesn't work.

- **A decorative underline/rule/eyebrow under a heading is usually a per-heading *authored* treatment, not an automatic "first heading of every section" style — measure it on every heading, h1 and h2, on every page.** It's tempting to codify "the site underlines section headings" as one blanket CSS rule keyed on `h1:first-child, h2:first-child` and move on. Confirmed wrong directly: a reference's signature yellow heading rule was on its section **H2s** ("Current Adventures", "Our Contributors", "All Articles") but *not* on most page-title **H1s** ("Adventures", "About Us", "Magazine", article titles) — while a *few* H1s did carry it (FAQs, adventure-detail) and a few section H2s were authored *without* it ("Experience the world with us"). A blanket first-heading rule got all of those wrong at once, and it survived because nobody measured the decoration per heading — only "does the underline exist on the site." Pull the `::after`/`border`/background of **each** heading individually (a quick `getComputedStyle(el, '::after')` sweep over every `h1`/`h2` in `main`) and reproduce the on/off state per heading via an opt-out (or opt-in) section style, rather than assuming a single structural selector captures an authored, inconsistent treatment.
- **`letter-spacing` on uppercase/label-style text is a very easy value to invent and never check.** A small positive tracking value (e.g. `0.02em`) "looks right" on uppercase text as a matter of typographic convention, so it's tempting to add reflexively to every nav link, breadcrumb, tab, button, and card title without measuring it — confirmed wrong at nine separate call sites across six files in one project, every single one of which measures `letter-spacing: normal` on the actual reference. This is exactly the kind of "obviously correct" convention this skill already warns about for margin resets — it applies just as much to letter-spacing.
- **An undefined CSS custom property fails silently, not loudly.** `var(--some-token)` referencing a property that was never defined anywhere in the codebase doesn't error or warn — the declaration is simply invalid at computed-value time and the property falls back to its initial/inherited value, so a hover or active-state color can be quietly doing nothing while looking like ordinary, intentional CSS. When auditing a component's states (hover, `aria-pressed`, `aria-selected`, etc.), grep the actual custom property name to confirm it's defined in the token file, not just present in the rule — a plausible-looking `var(--color-brand)` is worthless if `--color-brand` was never declared.
- **A screenshot can misread a font's weight, case, and color entirely.** A bold, same-color, mixed-case paragraph can look like a small uppercase gray "eyebrow" label at a glance (compression, unfamiliar font rendering, and small size all make this easy to misjudge) — confirmed wrong in exactly this way on a real build until `getComputedStyle()` on the actual element settled it. Any typographic detail that will drive a CSS rule (text-transform, font-weight, color, letter-spacing) needs its computed value pulled directly, not inferred from how it looks in an image.
- **A `getComputedStyle().fontFamily`/`fontWeight` match between reference and implementation is not proof the same font actually rendered on both.** These properties report the *declared* CSS value, not which font the browser resolved to — an implementation whose `@font-face` is missing, has a broken `src` path, or was never vendored (an empty `fonts/` folder is enough) will still report the intended `font-family` string unchanged while silently rendering a fallback font, so a computed-style diff alone can pass a page that visibly uses the wrong typeface. Same blind spot for weight: a declared `600` renders as a browser-synthesized fake-bold, not a real medium/semibold cut, if that weight was never loaded. Verify actual font loading directly instead of trusting the string match: `await document.fonts.ready; document.fonts.check('600 16px "Source Sans Pro"')` returns `false` if that exact family+weight never loaded. Check this on the implementation for every family/weight the measurement spec calls for, and cross-check the network/asset folder (e.g. `fonts/`) actually contains the file backing each `@font-face` — don't rely on the CSS declaration existing as proof the font itself is present.
- **Don't assume the reference scales its type responsively just because that's this skill's own mobile-first convention.** Many real sites hold heading sizes (and sometimes body text) completely fixed across every breakpoint — measure the actual `font-size`/`line-height` of each heading level at the narrowest and widest required widths before building any responsive type-scale variables; if they're identical, don't invent scaling that isn't there.
- **Confirm a repeating grid/list pattern by measuring bounding rects of multiple sibling items, not by eyeballing one card or a cropped screenshot.** A single item viewed in isolation can look like a horizontal list row when it's actually one cell of a wrapping multi-column grid (or vice versa) — pull `getBoundingClientRect()` for at least 3-4 consecutive instances and check whether they share a row (same `y`) before deciding on a grid vs. list variant.
- **A mobile/tablet nav drawer is often a completely different visual treatment from the main header it opens from** — a different background color, its own fixed positioning and dimensions, sliding in from an edge — not just the same header content reflowed. Measure the drawer specifically (its `position`, computed `width`/`height`, `background`, and how it's actually triggered — some sites use a CSS `:target` anchor rather than a JS click handler, so a plain `.click()` in automation may silently no-op) rather than assuming it inherits the main bar's styling.
- **When a layout genuinely reflows at a width that doesn't land on this skill's fixed 768/960/1200 tiers**, don't force-fit the assumption that it must be one of those three. Measure at a few more widths to find where the actual reflow happens (e.g. bisecting between 1024 and 1280), then map the finding onto the nearest fixed tier and note the approximation in the registry — don't silently apply the wrong tier's breakpoint and call it matched.
- **Checking a component's ancestor chain for a background color is not the same as checking the component's own styled sub-elements.** A card/teaser component is often composed of sibling divs (an image div and a separate "content" div) rather than one flat box — walking up from a heading through its *ancestors* only tells you whether the outer wrapper/section has a background; it says nothing about a sibling-level content panel that carries its own background independently. Confirmed wrong exactly this way: an ancestor-chain check on a featured-card's title found "transparent" all the way up, which was true, but missed that the card's separate content div (a descendant of the card, not an ancestor of anything checked) had its own solid gray background. When checking whether *a specific visual region* has a background, get that exact element and check its own `backgroundColor`/`background-image` directly — don't infer it from a chain that never actually included it.
- **A CSS value confirmed correct at one width is not confirmed correct across its whole breakpoint range.** A property that looks right at the breakpoint's tested width (e.g. 1200px) can still be badly wrong partway through that same tier (e.g. at 800px) if the reference scales the value continuously or steppedly with viewport width while the implementation uses one constant. When a measured value depends on more than just "which breakpoint tier," sample several widths within the tier (not only its starting width) before concluding a fixed value is an adequate match. **Corollary — read the computed value at each tier before assuming it scales at all; a state can be entirely off below one breakpoint and on above it.** Confirmed directly (a correction of an earlier wrong reading of this same card): the hero caption card does *not* gradually grow its overlap with viewport width — its `margin-top` is a flat `0` (no overlap; the card sits below the image) at every width below 1200px and only `-180px` (full overlap) at ≥1200px. An earlier pass had encoded a stepped `-32px/-140px/-180px` "growing overlap," which was simply a misread; pulling the actual computed `margin-top` at 375/768/960/1200/1280 settled it. Measure the computed value at each tier rather than interpolating a trend from one or two samples.
- **For an overlapping card/caption, measure its *height* (and `min-height`) too — not just its width, position, and whether it overlaps.** A card that overlaps a hero can match on x/width/overlap and still be visibly wrong because it collapses to hug its text instead of reserving a substantial height. Confirmed directly: an "Experience the world with us" caption card matched the reference on width (1192px), background (white), padding (0 28px), and overlap — but rendered 99px tall (fit-to-content) against the reference's 180px, because the reference sets a load-bearing `min-height: 180px` (with the text top-aligned and white space below) that no width/position/overlap check had captured. `min-height` is exactly the kind of "invisible unless you look for it" property that decides whether a card reads as a proper block or a thin strip — pull it explicitly, and check the card's rendered height against the reference's, whenever a card's fill looks off.
- **Known cross-browser rendering quirk, worth checking for on any image using both**: an `<img>` with explicit HTML `width`/`height` attributes *and* a CSS `aspect-ratio` can render at the attribute-derived intrinsic size instead of the CSS-computed one, silently ignoring the `aspect-ratio` rule (reproduced in an isolated test page outside any framework — this is a browser behavior, not a project-specific bug). If a sized `<img>` also carries `aspect-ratio`, verify the *actual rendered* box dimensions (not just that the CSS rule exists) and add `height: auto` alongside `aspect-ratio` if they don't match.

## Accessibility

Reproducing visual appearance is never a reason to regress accessibility. While validating:

- Use semantic HTML (the right element for the job, not a `div` styled to look like a button).
- Preserve or improve heading hierarchy — don't skip levels just because the reference's visual hierarchy doesn't match its heading levels.
- Ensure interactive elements are keyboard-navigable and have visible focus states, even if the reference site's own focus states were subtle or hard to observe.
- Provide appropriate labels and alt text.
- Use ARIA only where semantic HTML genuinely can't express the pattern (e.g. a custom tab interface), not as a default reflex.
- Reproduce accessible interactive states (disabled, expanded/collapsed, current-page nav indicators) rather than just their visual appearance.

If reproducing something exactly as the reference does it would mean sacrificing accessibility (e.g. the reference uses a color-contrast combination that fails WCAG, or a click target that's too small), prefer the accessible version and note the deviation rather than faithfully reproducing an accessibility problem.

**Fix a heading-order problem by changing the heading's level, never by relocating content.** When the reference has a heading-level skip (e.g. `h1` straight to `h3` with no `h2`), the fix is to change the offending heading's *level* in place (promote the `h3` to `h2`, or restyle a real `h2` to look like the reference's smaller heading) — not to move page content around so the outline happens to pass. Confirmed directly: an `h1 → h3` skip on a FAQ page was "fixed" by hoisting a "Need more help?" section to the top of the page so it could serve as the `h2`, which satisfied the audit while introducing a real content-order regression the reference never had. Heading level is a semantic attribute you may adjust for accessibility; content order is reference fidelity you may not quietly trade away for a green audit. If matching the reference's visual heading sizes and keeping a gap-free outline genuinely conflict, that's a deviation to raise with the user in the turn you find it, not to resolve by rearranging the page.

## Conservatism while validating

- Don't declare a page "pixel-perfect" or "complete" unless the comparison in this file has actually been run at the required breakpoints. If time/tooling constraints mean only some breakpoints were checked, say so explicitly in the report rather than implying full coverage.
- If a difference can't be resolved (e.g. a font isn't licensed for use, a background pattern can't be reliably extracted), don't fake it — use the closest reasonable substitute and record the deviation in the page registry instead of silently leaving it unmentioned.
- If two components look similar in this comparison pass but you're now noticing their actual behavior differs (e.g. one animates and one doesn't, one has a genuinely different content model), don't force them together retroactively just to reduce the component count — see `naming-rules.md`.
- When a subtle CSS mechanism is involved in reasoning about a fix (cascade specificity, `var()` fallback/invalid-at-computed-value behavior, margin collapsing, inheritance), work through the actual algorithm rather than trusting intuition about what "should" happen — intuition is exactly what produces confident-but-wrong conclusions here (e.g. assuming that omitting a declaration produces the same result as an explicit declaration that resolves to `inherit`; it doesn't, because cascade resolution happens before the invalid-value fallback is applied). When reproducing an effect that depends on such a mechanism, prefer the deterministic, explicit equivalent (e.g. `font-family: inherit` instead of leaning on an undefined-variable quirk) over replicating the exact mechanism, so it doesn't quietly depend on subtle behavior a future reader (or browser) might not reproduce identically.
